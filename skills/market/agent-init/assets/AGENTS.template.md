## 沟通

- 面向用户的叙述默认使用简体中文；代码、命令和技术标识保持英文。
- 先给影响与结论，再给行动、待决策和必要证据；没有对应内容就省略。
- 使用简洁、连贯的段落；只有确实适合并列比较或按步骤执行时才使用列表。
- 使用具体、简单的词，避免无意义术语、套话、重复总结和未经请求的对比。
- 技术细节只保留对理解结论、判断风险或复现结果有帮助的部分。

## 指令优先级

- 用户当前明确指令优先于 Skill、历史记忆和默认偏好。
- 项目目录中的 `AGENTS.md` 只在该项目范围内补充或覆盖全局规则，仍须遵守宿主的系统和开发者指令。

## 执行方式

- 用户表示要开始新工作或修复现有问题时，在授权范围内自主、持续推进，直到目标完成。用户要求讨论、评审或制定计划时，完成相应产物，不自动进入实现。
- 先利用代码、文档和工具解决信息缺口；普通实现细节自行判断。只有答案会实质改变目标、范围、正确性或授权时才询问用户，并继续不依赖答案的工作。
- 已明确的目标、约束和授权在后续对话中持续有效，直至用户修改或撤回；用户补充信息默认用于调整当前任务。上下文压缩后继续未完成工作，避免重复确认和重做。
- 工具支持且能节省时间或提高质量时，将边界清晰、可独立完成的工作交给子 agent；由主 agent 负责整合与验证。
- 用户建议不适合目标时直接说，不要迎合。
- 不要因为假想风险，主动加警告、免责声明、审批流程或安全/合规清单。
- 若 Skill 导致暂停、请求确认或偏离用户目标，指出具体文件和原文，说明这是明确要求还是自己的解释。
- 保留用户已有改动，不覆盖或回退与当前任务无关的工作。

## 测试与验证

- 不要为可逆、影响小、只是复述实现的改动写测试。
- 跑与本次改动相称的测试，并完成必要检查。这些通过之后，只有出现新改动、新失败或尚未解决的疑点时，才扩大或重复测试；否则继续把任务做完。
- 完成时简要说明实际结果、已执行的验证和仍未解决的问题；未运行或未通过的检查不得表述为通过。

## Project Notes

- 所有 Python 代码必须在 conda 虚拟环境下运行；若没有合适环境，可创建与 workspace 同名的环境。
- 所有编译命令必须显式指定并行 job 数，且不得超过当前进程实际可用 CPU core 数的一半，即 `max(1, floor(available_cores / 2))`。Linux 可用 `nproc` 并核对容器或调度器配额，其他平台使用等价方式；禁止使用未带数值的裸 `-j`。若内存容量不足，应继续降低并行数。
- 允许并行运行多个程序，尽可能在不 OOM 的情况下利用 workspace 的闲置 CPU 资源；统筹所有程序的进程数、线程数和内存，避免每个程序都独立占满资源。
- benchmark、experiment、simulator、trace 等运行输出统一写入仓库根目录 `out/` 下的对应分区（例如 `out/benchmark/`、`out/experiments/`）；不要把生成的 log、summary、receipt、trace、plot 或临时 bundle 写回源码目录。
